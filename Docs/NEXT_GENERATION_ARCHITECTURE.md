# ワリカンジ次期アーキテクチャ

## 目的

ワリカンジを、割り勘計算だけでなく、複数人イベントの準備・当日進行・精算・終了後まで支援できる構造へ拡張する。

114項目を一度に画面へ追加せず、イベント種類と機能設定に応じて必要な機能だけを表示する。既存のイベント、費用、精算データは維持し、段階的に移行する。

## 守るべき原則

1. 参加者回答と共同編集権限は別に扱う。
2. 支払い済みへの変更は、権限を持つ幹事か正式な決済連携だけが行える。
3. 機能をOFFにしても関連データは削除しない。
4. 金額は現在と同じく通貨の最小単位を整数で保存する。
5. イベント、参加者、部、回答、タスクには変更されないUUIDを割り当てる。
6. 進行アシスタントは保存データから候補を導出し、同じ情報を別管理しない。
7. 外部サービスがなくても、現在の費用記録と精算は利用できる。
8. 共有時の権限判定は最終的にサーバー側でも検証し、端末表示だけを安全境界にしない。

## ドメイン構造

```text
Event
├── 基本情報（名称、日時、場所、通貨）
├── EventPlanningState
│   ├── FeatureConfiguration
│   ├── AccessPolicy
│   ├── EventPart[]
│   ├── ParticipantResponse[]
│   ├── EventTask[]
│   └── ActivityRecord[]
├── EventParticipant[]
├── Expense[]
└── Transfer[]
```

`EventPlanningState`を次期機能の境界にする。既存の計算処理は`EventParticipant`、`Expense`、`Transfer`を引き続き利用し、計画機能の追加によって精算処理を壊さない。

## 機能ON/OFF

機能は文字列キーで保存する。固定enumだけにすると、新しい機能を追加したアプリで保存したデータを旧版が読めなくなるため、未知のキーも保持できる型にする。

テンプレートはイベント種類ごとの初期値だけを提供する。利用者が変更した後は、イベント種類を変更しても勝手に上書きしない。

初期の機能群は次の単位にまとめる。

- 出欠・同伴者
- 日程投票
- 店候補・店投票
- 予約・キャンセル期限
- 複数部
- 食事制限
- 一杯目
- 集合・到着
- 連絡
- 天気・代替案
- 席順
- 受付
- 事前徴収
- 予算
- タスク・持ち物
- タイムライン
- サプライズ
- 共有アルバム
- 終了後まとめ
- グループ・店舗履歴
- 旅行、車、宿泊、チケットなどのイベント別パック

## 権限モデル

役割は次の4種類を基本とする。

| 役割 | 説明 |
|---|---|
| 主幹事 | 所有者。権限設定、精算ロック解除、幹事変更が可能 |
| 共同幹事 | 主幹事が許可した編集を実行可能 |
| 参加者 | 回答と、自分に許可された操作のみ可能 |
| 閲覧のみ | 表示のみ |

権限は役割の初期値に加え、メンバー単位で許可・拒否を上書きできる。拒否を許可より優先する。

最低限必要な権限キー：

- イベント情報編集
- 参加者管理
- 回答管理
- 店候補管理
- 予約管理
- 費用追加
- 費用承認
- 費用編集
- 精算計算
- 支払い状況編集
- 精算ロック管理
- タスク管理
- 連絡送信
- 権限管理

ローカル専用イベントでは現在の端末所有者を主幹事として扱う。共有機能導入後は、共有メンバーIDとイベント参加者IDを必要に応じて関連付ける。

## 参加者回答

回答はイベント編集と別の保存単位にする。

- 出欠：参加、不参加、未定、未回答
- 同伴者
- 参加開始・退出予定
- 部ごとの参加可否
- 食事制限
- 到着状況
- 任意質問への回答

共有リンクから回答できても、イベント名、費用、精算、他人の回答を編集できることにはならない。

## 複数部

一次会、二次会、旅行日程などを`EventPart`として共通化する。

各部は名称、開始・終了、場所、参加者、並び順を持つ。費用は必要に応じて部IDへ関連付ける。既存費用の部IDは未設定のまま扱える。

## 費用承認と支払い

費用には将来、下書き・承認待ち・承認済み・却下の状態を追加する。承認済みだけを正式な精算へ含める設定を選択可能にする。

支払い状況の変更元を記録する。

- 権限を持つ幹事による手動確認
- 正式な決済サービスによる確認

参加者本人による自己申告だけで支払い済みにはしない。

## 編集履歴

履歴は追記型とし、少なくとも次を保存する。

- 操作ID
- 操作者IDまたは端末操作
- 操作日時
- 対象種類と対象ID
- 操作種類
- 変更概要
- 操作元（ローカル、共有、決済サービス）

ローカル履歴は利用者向けの確認機能であり、改ざん不能な監査証跡とはみなさない。共同編集開始後はサーバー側にも履歴を保存する。

## 進行アシスタント

全イベント共通の中心機能とする。各機能から未完了状態を収集し、優先度、期限、対象画面を付けて「次にやること」を生成する。

優先順位の基本：

1. 安全・緊急連絡
2. 期限超過または当日期限
3. 予約・キャンセル・支払い
4. 未回答・未割当
5. 任意の改善提案

表示項目は保存せず、イベント状態から毎回生成する。利用者が明示的に非表示にした提案だけを別途記録する。

## 共有方式

共有は2経路に分ける。

### 回答専用リンク

- アカウントなしでも利用できる方式を検討
- 回答可能な質問と期限だけを公開
- 推測困難なトークン、失効、再発行、参加承認に対応
- 精算や秘密メモなどは返さない

### 共同編集

- 原則として本人識別が必要
- イベントごとの役割と権限をサーバーで検証
- 更新番号による競合検出
- オフライン変更の再送と競合表示
- 精算ロック中の変更を拒否

バックエンド、認証、通知サービスは運用費とプライバシーに影響するため、実装前に選定する。

## データ移行

- 既存JSONに次期フィールドがない場合は、イベント種類の標準テンプレートから初期状態を生成する。
- 既存参加者、費用、送金IDは変更しない。
- 未知の機能キーは削除せず再保存する。
- 将来の破壊的変更に備え、計画状態へ形式バージョンを持たせる。
- バックアップ形式は既存イベントJSONを内包するため、新フィールドも自動的に対象となる。

## プライバシー分類

特に慎重に扱う情報：

- アレルギー、宗教・文化上の食事制限
- 子ども区分
- 現在地、最寄り駅、帰宅方法
- 電話番号、会社名、予約番号
- 支払い状況、決済情報
- 秘密メモ、サプライズ情報

これらは初期状態で共有せず、目的、公開相手、保存期間を画面上で明示する。現在地は本人の明示操作と期限付き共有を必須とする。

## 実装境界

最初の基盤実装では、外部通信を追加しない。次をローカルデータとして導入する。

- 機能キーとイベント種類別テンプレート
- 役割、権限、アクセス方針
- 複数部
- 参加状態の基本形
- タスクの基本形
- 履歴の基本形
- 進行アシスタントの拡張可能なルール

店検索、予約、天気、交通、通知、決済、共有同期は、それぞれ正式な提供元と利用条件を確認してから接続する。
